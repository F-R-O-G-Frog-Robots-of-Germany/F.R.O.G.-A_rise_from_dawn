# Quick robot bring-up, Pedro tuning, and constants reference

Goal: get the basic robot driving, localized, collecting, and shooting reliably as quickly as practical, then validate a small set of autonomous routes without Limelight, AprilTags, or Butine.

## Scope, assumptions, and how to use this guide

Prepared from the repository on 2026-11-11. This document makes no code or hardware changes. Measurements and later source edits are work to perform when the assembled robot is available. The current numbers are a snapshot, not certified robot settings. Recheck symbols after your upcoming patches.

The first part is the shortest useful commissioning order. The second part groups the constants into **A: settings you will probably change** and **B: settings to leave alone during basic tuning**. The source inventory includes line numbers, current declarations, and configuration setter values, so there is no need for a third Markdown file.

Use the existing hardware and software architecture: FTC SDK 12.0.0, Pedro core/revhub 3.0.1, tuning 1.0.1, Mecanum, Pinpoint, and Foresight. Those versions are declared in `build.dependencies.gradle`. Avoid following Pedro 2 guides that ask for old `FollowerConstants` or unrelated PIDF classes; this repository registers Pedro 3 procedures in `core/pedro/Tuning.java`.

The [camera-free competition plan](No-Limelight-Competition-Plan.md) covers future isolation of the vision/planner integration. Do not disconnect or delete it as part of following this document today.

## 1. Priorities when time is limited

| Priority | Work | Result required before moving on |
| --- | --- | --- |
| 1 | Confirm wiring, hardware names, safe servo geometry, encoder conversion | Init cannot unexpectedly drive a linkage into a stop; names resolve. |
| 2 | Drive motor directions and Pinpoint calibration | Correct manual motion and trustworthy measured pose. |
| 3 | Foresight AutoTune and short follower tests | Repeatable straight, strafe, turn, and curve behavior. |
| 4 | Intake thresholds and flower positions | Repeatable collection/full detection and unobstructed lift/lower. |
| 5 | One fixed RPM/hood shot under the competition controller | Reliable feed and shot at a marked location. |
| 6 | One chosen autonomous and its BLUE counterpart | Repeatable pickup, shot, parking, and correct handoff. |
| Later | Distance curves, more routes, maximum speed optimization | Expand only after the basic configuration works. |

If time runs out, reduce the route and shot-distance scope. A measured fixed shot and a thoroughly practiced existing route are more useful than unmeasured curves and many partially tested routes. None of these stages requires Butine tuning.

## 2. Prepare the robot and record a baseline

- Record the code revision, battery voltage, robot mass/configuration, tire condition, field surface, and any existing tuning values before changing them.
- Check wheel order, mecanum roller orientation, odometry-pod contact, belt/gear tension, and mechanism clearance.
- For initial direction checks, lift/support the drivetrain. Perform odometry and path tests on the actual driving surface afterward.
- Confirm all mechanism motions that can occur during Init before initializing competition modes: the flower intake commands UP and the hood commands its default angle.
- There is no calibration flag preventing filler hood settings from being used. Calibrate or mechanically isolate the linkage before allowing unknown travel.
- The shooter FLOAT state is an active spinning state: `FLOAT_RPM=3000`. Do not interpret “FLOAT” in this subsystem as “motor off.” The dedicated tuner has separate enable controls.
- Use a written log rather than memory. Change one related set of values at a time and rebuild/deploy before judging source changes.

## 3. Set measurement conventions before tuning

- Pedro field positions and current localizer configuration use inches; headings inside `Pose` are radians.
- `OptimalPoses` constructs ideal route coordinates through a degrees pose factory. Its `hotfix(dx, dy, ddeg)` arguments are inches, inches, degrees.
- Intake range readings and thresholds use millimeters.
- Shooter targets use revolutions per minute (RPM); the competition PIDF calculation uses encoder ticks per second internally.
- Servo positions are normalized 0 to 1; a hood angle in degrees is a separate physical quantity.
- Timeouts named `...SECONDS` use seconds. Hood settling uses milliseconds. Sensor polling uses nanoseconds.
- BLUE route mirroring uses the existing transform around field center `(72,72)`; preserve it when applying RED-side corrections.

Do not mix encoder counts at the motor shaft with flywheel revolutions. Define `GEAR_RATIO` consistently as encoder-shaft revolutions per flywheel revolution if `TICKS_PER_REV` is encoder ticks per encoder-shaft revolution. Their product is the actual counts per flywheel revolution used by this code. Verify that product experimentally and with the motor/encoder specification.

## 4. Tune the drivetrain first

`core/pedro/Tuning.java` already registers Mecanum, Pinpoint, Foresight, and Tests procedures. Use the robot-hosted AutoTune interface while connected to the Robot Controller. Pedro documents the default address as `http://192.168.43.1:10158`; use the robot's actual network address if different. The official [tuning overview](https://pedropathing.com/docs/pathing/tuning) confirms the drivetrain, localization, then Foresight sequence.

1. Run **Mecanum Tuner** and enter the four actual hardware names.
2. Follow its individual motor-direction checks. Current source reverses both left motors and leaves both right motors forward; that is a starting configuration, not proof that the assembled robot is correct.
3. Copy the accepted names and directions into `Constants.drivetrainConfig` during the later tuning work.
4. Rebuild and deploy. Use **Tests → DRIVING** for controlled low-input motion checks.
5. Confirm forward, left strafe, and positive counterclockwise turning. Fix motor ordering/directions before changing controller gains.

The Mecanum tuner produces a configuration; do not assume results are automatically persisted into Java source. The active competition follower is built from `Constants.java`.

## 5. Calibrate and verify Pinpoint before Foresight

### Values to establish

- Correct hardware name and actual pod model.
- Forward and strafe encoder directions.
- Forward/strafe pod offsets in the configured inch units.
- Custom ticks-per-inch only if using a custom pod; do not substitute a guessed scalar for a known supported pod type.

### Procedure

1. Run **Pinpoint Tuner**. Its default is hardware name `pinpoint`, FOUR_BAR pods; change the selection to match hardware.
2. For CUSTOM pods, enter an accurately measured push distance; the local procedure defaults to 48 inches. Use an actual measured distance, not a nominal tile count with gaps ignored.
3. Follow forward push and left push direction identification.
4. Follow the offset-identification instruction: rotate in place 180 degrees counterclockwise, then stop. Repeat to check consistency rather than trusting a single run.
5. Copy the resulting name, pod type/scalar, directions, and offsets into `Constants.localizerConfig`, preserving inch units. The current zero offsets must be verified or replaced; they are not a general default for a real pod installation.
6. Rebuild/deploy and run **Tests → POSE** for hand-pushed measurements. Use **LOCALIZATION** only after reading its movement instructions; it commands the drivetrain.
7. Push a measured 24 or 48 inches forward and back, then left and back. Rotate through known angles and return to the starting mark. Check independent measurement of position and heading, not just whether the displayed pose returns near zero.

Suggested initial acceptance targets, chosen for this plan rather than guaranteed by Pedro: within about 1 inch over a measured 48-inch straight push and within about 2 degrees after a known full turn. Tighten them if your pickup or shot needs smaller errors. Repeat measurements; a systematic scale error or position jump during rotation must be fixed before tuning paths.

The local `Tests` procedure accepts the existing Foresight supplier and still provides POSE/LOCALIZATION selections. You do not need to rewrite `Tuning.tests()` just to run those selections. Official [localization guidance](https://pedropathing.com/docs/pathing/tuning/localization) supports checking forward +X and left +Y before follower tuning.

## 6. Run Foresight AutoTune and save its results

Do this on the actual field surface with normal robot mass and a healthy battery. Several local procedures command substantial power, including full-power velocity tests; reducing a later follower velocity limit does not limit those tuner commands. Read each stage's instructions and reserve acceleration, braking, and coast space beyond the entered distance.

The registered **Foresight Tuner** runs velocity, deceleration, heading, braking, and translational identification. Follow the browser's stage order. Record the complete generated Java configuration; it is more reliable than transcribing only one displayed gain. This workflow and the generated configuration are described by Pedro's official [Foresight tuning guide](https://pedropathing.com/docs/pathing/tuning/foresight).

### Map the results into the existing active configuration

| Tuner result | Destination in `Constants.foresightConfig` |
| --- | --- |
| Maximum forward / strafe velocity | `maxAchievableForwardVelocity`, `maxAchievableStrafeVelocity` |
| Natural forward / strafe deceleration | `naturalForwardDeceleration`, `naturalStrafeDeceleration` |
| Heading kP | `headingFeedback` controller |
| Heading linear / quadratic braking | X/Y entries of `headingBrakeCoefficients` |
| Forward / strafe linear braking | Forward/strafe diagonal entries of `linearBrakeCoefficients` |
| Forward / strafe quadratic braking | Forward/strafe diagonal entries of `quadraticBrakeCoefficients` |
| Primary / secondary translational gains | Generated forward/strafe controller expressions |
| Coast / brake feedforward | `coast` / `brake` controllers |

The current source has one proportional controller per translational axis. The local tuner emits piecewise primary/secondary controllers with a 2.5 breakpoint. Preserve the generated controller structure when adopting its results; two measured gains cannot be represented by blindly replacing a single number. Review the generated block against the installed library and retain intentional path limits rather than erasing the entire file.

Illustrative mapping, not measured robot values or a patch to apply now:

```java

c.headingBrakeCoefficients.set(Vector2D.cartesian(measuredHeadingLinear, measuredHeadingQuadratic));

c.quadraticBrakeCoefficients.set(Matrix.diag(measuredForwardQuadratic, measuredStrafeQuadratic));
```

Variables prefixed `measured` above are placeholders, not fields available in this repository. Do not paste this snippet without actual results.

### Path limits versus physical identification

Measured maximum achievable velocity describes the robot. A chosen maximum velocity constraint describes how fast a particular configuration is allowed to ask it to move. Keep those concepts separate: lower the operating constraint for cautious initial path tests without falsifying the measured maximum. Likewise, natural deceleration is measured behavior, while acceleration/deceleration constraints are operating choices.

The current values 75, 59, 46, 79, 200 and the braking/controller coefficients are unverified on the assembled robot. Do not replace them with another team's numbers. Start below measured capability and increase operating limits only after the same route repeats successfully. Check installed-library units for every constraint, especially timeout and parametric constraints; their names do not imply the same units as the autonomous base's second-based watchdog.

`core/pedro/PathConstraints.java` contains an `autoPilot` configuration with suspiciously small velocity/deceleration values. Repository search currently finds no callers. Tuning that block will not tune the active follower. Leave it alone unless a later patch explicitly connects it and its units are reviewed.

## 7. Validate the follower before editing routes

Use the locally available **Tests** options: HOLD, LINE, CURVED, INTERPOLATION_CURVED, LOCALIZATION, POSE, and DRIVING. Do not rely on a differently named test from another Pedro version.

1. Start with POSE and DRIVING checks already passed.
2. Run a short LINE test with a suitably reduced operating constraint, then a longer measured line.
3. Run HOLD and confirm it settles without sustained oscillation.
4. Run CURVED, then INTERPOLATION_CURVED, in clear space.
5. Repeat each useful test at least three times and check its physical finish, heading, overshoot, completion time, and trial-to-trial spread.
6. Repeat representative paths with normal mechanism load and another battery state.

The local LINE/curve tests can keep alternating paths until you stop the OpMode. Count completed passes deliberately and use Stop when finished; do not assume the test ends after its first arrival. LOCALIZATION is driver-controlled in this repository, while POSE is for hand movement.

Suggested starting acceptance: three finishes within a roughly 1-inch / 2-degree window for a short basic path, no persistent oscillation, and no timeout. These are planning targets; the actual pickup and scoring geometry determines the final tolerance. Measure the robot's footprint and path clearance separately.

| Symptom | Inspect first | Avoid doing first |
| --- | --- | --- |
| Wrong direction or spinning instead of translating | Motor names, order, directions | Increase gains |
| Pose distance wrong on a hand push | Pod model, units, encoder scale | Offset every route endpoint |
| Translation reported during in-place rotation | Pod offsets and mounting | Add translational gain |
| Endpoint oscillation with correct odometry | Identified feedback/braking and operating limits | Remove end constraints |
| Overshoot at speed | Measured braking behavior and selected limits | Add arbitrary route hotfixes |
| Accurate pose but wrong physical route | Start placement, mirroring, route geometry | Retune encoder scale |
| Follower never finishes | Completion constraints, observed residual error, watchdog | Set timeouts unbounded |

## 8. Calibrate intake and flower mechanisms

### Flower intake

`FlowerIntake` uses one shared DOWN position (0) and one shared UP position (1) for both servos. Init immediately commands UP. Determine safe positions with the linkage understood and motion supervised. Confirm both sides move in the intended mechanical direction; mirrored mounting may need direction handling or separate endpoints in a later code change. There are no independent left/right position constants in the current implementation. If a shared pair cannot move both sides correctly, record that limitation rather than forcing the mechanism with full travel.

### Intake full-load sensing

`EMPTY_UPPER_DISTANCE` and `EMPTY_LOWER_DISTANCE` are both `mm(0)` placeholders. Despite their names, `loaded()` returns true when **both valid measured distances are less than their corresponding threshold**. With normal nonnegative distance readings, zero thresholds do not detect a full load.

1. Record lower/upper sensor distances for empty, partial, and full loading with the real game pieces.
2. Repeat across realistic orientations and sensor noise. Readings must be finite and physically plausible.
3. Select a threshold for each sensor between its occupied and unoccupied distributions, if those distributions separate.
4. Check the actual combined condition: both must pass. One sensor below its threshold alone must not report a full load.
5. If the distributions overlap, improve placement or later sensing logic; do not claim a reliable threshold exists.
6. Verify the full-load latch stops collection and does not restart because of one dropout; verify the expected reset/feed/collection cycle.
7. Check detection latency. The current sensor polling interval is 300 ms; assess it against real piece speed before deciding whether to change it.

Example only: if one sensor reads 20–30 mm when occupied and 70–90 mm when clear, 50 mm is a candidate for that sensor. Those invented observations do not establish either actual threshold.

`intakePow` and `transferPow` are currently integers with value 1. Fractional power is not representable without a later type/code change. Verify directions and jam behavior at controlled conditions before full-load operation. `transferStallCurrent` is declared but is not an implemented calibrated stall-protection threshold.

## 9. Calibrate the shooter before collecting shot data

### Encoder scale and mechanical limits come first

1. Verify `TICKS_PER_REV=2048` and `GEAR_RATIO=1` against the actual encoder and gearing. Confirm displayed flywheel RPM with an independent reference when possible.
2. Check both flywheel directions and the sign of left encoder feedback. The competition controller reads the left encoder and applies the same power command to both motors; right motor speed is not independently regulated there.
3. Establish a measured and mechanically acceptable maximum RPM. `MAX_RPM=6000` is a placeholder cap, not a rating inferred from hardware.
4. Measure safe hood minimum/maximum angles and their matching normalized servo positions. Avoid assuming the physical mechanism can traverse 0–90 degrees or servo 0–1.
5. Check intermediate angles; the mapping assumes a linear linkage. Record a later implementation need if interpolation is materially wrong.
6. Set a safe default hood angle inside those bounds and measure settling time over worst-case relevant travel. The active 250 ms is provisional and does not measure actual servo position.

### Important controller mismatch

`ShooterPidfTuner` uses the hub's encoder velocity controller. Competition `Shooter` uses its own power-output PIDF calculation in RUN_WITHOUT_ENCODER. Identical numeric PIDF values do not imply identical behavior, so do not copy tuned hub gains into `Shooter.K_P/K_I/K_D/K_F` as if they were interchangeable.

The competition regulator also uses full power when more than `PIDF_RANGE_RPM` below target and zero power above target; PIDF acts in its remaining band. Tune and observe the actual competition behavior after encoder conversion is correct. Feeding and the FLOAT background speed can change what you observe. Review the current regulator before diagnosing every oscillation as a proportional-gain issue.

One useful diagnostic from the current equation: at 3000 RPM and 2048 effective ticks/rev, target speed is 102400 ticks/s and the configured feedforward term alone is `0.00017 * 102400 = 17.408`, above normalized motor power. This calculation does not prove the right replacement gain, but it is strong evidence that encoder scale and competition feedforward units must be checked. Do not accept the defaults merely because the tuner displays an RPM.

For later custom-controller tuning, observe steady-state power and target tick rate to estimate a feedforward starting point (`power / ticksPerSecond` in this implementation's units), then validate feedback response and recovery under load. Do not raise the 70-RPM feeding tolerance just to hide a controller that cannot hold speed. Integral and derivative gains require consistent time/error units and logged response; hardware data is needed for their final values.

### Fastest useful shot setup

Start with a single marked shooting position and a measured fixed RPM/hood pair. In competition INIT, gamepad 2 X selects fixed/model mode, bumpers adjust fixed RPM by 100, and D-pad up/down adjusts fixed hood by 1 degree. Validate RPM stability, hood settling, feeding, and scoring under the competition controller.

In Main during the match, fixed/model selection and RPM adjustment exist, but the INIT hood D-pad editor is not a match-time hood editor. Choose the intended hood before Start. `DEFAULT_FIXED_RPM=false` currently starts in model mode, whose active curves are filler 3000 RPM and 45 degrees.

Feeding readiness is initially gated, then an active shot is latched until explicitly stopped. Do not assume the code continuously suspends an already-started feed whenever RPM falls outside tolerance. Test the actual release/stop behavior and jam recovery.

## 10. Fit distance-based shots only after the fixed shot works

The existing [shooter guide](TeamCode/Shooter-Hood-Tuning.md) explains tuner controls, session-only captures, and paired regressions. Use its workflow, but check current source when behavior differs: current `Shooter.nearest_hive()` selects TOP when `robotY > 72`, otherwise BOTTOM. It is a field-half selector, not a comparison of both Euclidean distances. Do not use the old guide's 71.5 boundary when collecting current data.

The shot-distance input is horizontal distance in inches from robot pose to the selected alliance hive. Hive Z is stored but is not included in that horizontal distance.

1. Collect repeated successful shot pairs at more than three distinct distances in the region you will use.
2. Each row is one matched `(distance, measured RPM, commanded/measured hood-angle reference)` pair. Record the real angle calibration separately; the code has no hood-angle feedback.
3. At each distance, find a repeatable RPM/angle pair; for the current intended strategy compare angles and retain the lowest reliably successful RPM with its matching angle.
4. Fit RPM and hood angle separately against the same distance rows.
5. Copy the RPM coefficients into `DISTANCE_A/B/C` and hood coefficients into `HOOD_DISTANCE_A/B/C` during later source editing.
6. Rebuild, deploy, and validate fitted pairs both at and between sample distances under the competition controller.
7. Do not assume output clamping makes extrapolation valid. Current code has no calibrated-distance domain guard.

```text
RPM(d)     = DISTANCE_A*d^2 + DISTANCE_B*d + DISTANCE_C
HoodDeg(d) = HOOD_DISTANCE_A*d^2 + HOOD_DISTANCE_B*d + HOOD_DISTANCE_C

Desmos regressions using the same rows:
y_1 ~ a*x_1^2 + b*x_1 + c
z_1 ~ p*x_1^2 + q*x_1 + r
```

The dedicated shooter tuner begins at `(9,9,0 radians)` and does not drive the robot or intake. Put it at that physical reference or use a measured setup consistent with its displayed pose; repositioning without correct odometry invalidates the displayed distance. Tuner coefficients and captures are session-only. Save results explicitly and retest after copying to the source.

## 11. Tune one autonomous route, then expand

1. Pick an existing route with enough physical clearance and a manageable number of actions. No route is certified merely because it compiles.
2. Place the robot at its exact declared start, with correct heading and alliance.
3. Check ideal route geometry in `OptimalPoses`, then inspect that route's local constants and `hotfix(...)` expressions.
4. Correct field-specific offsets in the route's existing hotfix declarations. Keep ideal geometry unchanged unless the intended route changes. Corrections are applied before BLUE mirroring.
5. First verify travel and clearances, then flower lowering/lifting timing, then pickup, then shot duration and final park.
6. Measure actual timing. Typical named knobs include `SHOT_DURATION_SECONDS`, `...LOWER_AFTER_SECONDS`, and route-specific garden/estimated-path timing values. See the full inventory below for each declaration.
7. Verify `PATH_TIMEOUT_SECONDS=8`, `SHOOTER_WAIT_TIMEOUT_SECONDS=3`, and `LIFT_AFTER=1` against actual operation. Change a watchdog only with evidence of a legitimate action duration; a stuck mechanism or poor follower tune is a fault to fix.
8. Repeat at least three complete trials on RED, then verify the BLUE counterpart on the physical field.
9. Run the Auto-to-TeleOp transition promptly without relocating the robot. Stored pose is valid for 200 seconds; a stale pose can still be physically wrong if the robot was moved during that window.

TeleOp manual resets are gamepad 2 D-pad right for RED reference `(9,9)` and left for `(9,133)`, with the existing alliance transform. `reset_pose` sets a 90-degree RED reference heading, mirrored for BLUE. Only reset while physically at the matching reference with matching orientation. The generic fallback is also `(9,9,90 degrees)` before alliance handling; it is not the shooter tuner's `(9,9,0)` reference.

### Group A — settings you will probably change

**A1: Measure before normal operation.** Hardware names/directions, pod type/scalar/offsets, shooter encoder conversion, mechanical RPM limits, safe hood endpoints/default, flower positions, and intake distance thresholds.

**A2: Identify on the assembled drivetrain.** Foresight translational/heading controllers, coast/brake feedforward, measured achievable velocities, natural deceleration, and braking matrices. Use the registered tuner and preserve complete expressions.

**A3: Adjust for the chosen behavior after A1/A2.** Operating velocity/acceleration/braking constraints, reliable shot RPM/hood, custom shooter control gains, feed readiness tolerance, and route-local hotfix/timing values. Completion constraints belong here only after measuring residual errors and checking units.

**A4: Driver/setup choices.** Deadband, fallback/reference poses only when the physical reference changes, fixed/model default, competition diagnostics settings, and driver adjustment step sizes. These are not measured drivetrain properties.
