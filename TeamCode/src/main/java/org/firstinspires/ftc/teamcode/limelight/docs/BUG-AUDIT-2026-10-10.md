# Limelight and Butine bug audit — 10 October 2026

Goal: trace the Java port's input classes and state transitions, calculate independent expected outputs, fix defects, and retain fast planning and simple calls.

The audited implementation uses Java, preserves drive-over pickup, leaves intake and shooting to the caller, and does not integrate into competition autonomous. The three bench OpModes remain `@Disabled`.

Run `powershell -ExecutionPolicy Bypass -File tools\limelight-audit\run.ps1` from the repository. Java 17, Android SDK platform 35, and the cached FTC 12.0.0/Pedro core 3.0.1 dependencies are required. `-SdkRoot` and `-GradleCache` override locations. The script generates outputs only beneath the ignored `build/limelight-audit` directory.

The script first compiles production classes against **real SDK signatures**, using Java 8 source/target compatibility. It then compiles a separate camera test version against deliberately small transport stand-ins in `tools/limelight-audit/fixtures`. Those fixtures allow deterministic result injection without camera hardware or Android logging/JSON services; they do not establish hardware behavior or SDK compatibility and never belong in Android production/test source sets. The entire package, including its bench OpModes, was also separately compiled against the installed real libraries and the project's previously compiled classes.

This is equivalence-class, boundary, fault and randomized testing, with exhaustive reference searches on small fields. It is not a claim that every possible floating-point value, timing interleaving or hardware failure was exhaustively enumerated. No robot driving or camera calibration was performed.

## Defects corrected

| Area | Failing behavior before audit | Corrected result |
|---|---|---|
| Detector confidence | Dividing raw fractional confidence by 100 put ordinary detections below the map's 0.25 threshold | Preserve raw fractions; explicit `confidenceScale = 0.01` is available for verified percentage firmware |
| Camera restart | Lower camera uptime after a reboot could freeze publication forever | A fresh Control Hub receipt can begin a new camera epoch; older receipts remain rejected |
| Cached freshness | Pose/target getters could remain usable indefinitely when callers stopped polling | Getter age advances independently; stale cached poses and detector evidence expire |
| Initialization | An exception partway through initialization could leave camera polling alive | Both initialization paths release the device and expose failure |
| Pose history | A 64-entry ring overwritten every 1 ms lost the requested 500 ms latency window | Sample into 10 ms buckets, retaining recent interpolation and at least the intended history window at fast loop rates |
| Pinhole projection | Off-axis lateral displacement omitted the camera's pitch transformation | Project the full optical ray onto the floor |
| Map visibility | A level camera's horizontal wedge could erase floor targets outside its vertical field of view | The calibrated pinhole frustum checks horizontal and vertical optical angles |
| Map ordering | An out-of-order frame could erase newer detections | Reject sequences less than or equal to the processed sequence |
| Work bounds | Invalid/null observations bypassed the per-frame scan cap; reduced capacity could remain oversized | Count inspected entries, including rejects; shrink tracks on the next usable frame |
| Motion arithmetic | Finite large speed/acceleration values overflowed intermediate products | Stable triangular/trapezoidal arithmetic; reject nonrepresentable distances/times explicitly |
| Planner input/output | Nonfinite headings and malformed public runs could reach execution | Validate poses, run times, lengths and duplicate IDs; filter invalid candidates |
| Pickup dwell | Dwell contributed to predictions but was never executed | Nonblocking dwell ticks; leaving the pickup during dwell is a miss |
| Runner exceptions | A failed drive dispatch could leave the runner marked active | Abort and attempt drive stop; preserve the original exception and any secondary stop error |
| Empty plan | A declined collection could signal completion even away from the depot | Return `false` with `IDLE`; it is not a completed return to score |
| Changed track identity | Camera redetection before arrival could leave the collected target in the map | Remove a conservative nearby replacement without removing a separate neighbor |
| Failed-target history | A full exclusion list could fail to remember the latest unreachable target | Evict the oldest exclusion and retain the newest, capped at 64 |
| Pedro transitions | Stale algorithm busy state after stop/manual control; inherited half-speed constraint on later paths | Gate busy on follower mode; release previous path constraints before choosing a new limit |
| Path start | Previously built leg origins could differ from the live robot pose | Build each dispatched line from the follower's current pose |
| Relocalization | Move-out-and-return could look stationary at capture; late fixes could be accepted | Track motion during the whole look window; check deadline before accepting a correction |
| Correction failures | Drive pose-setting exceptions could leave AprilTag pipeline selected | Restore detector pipeline before propagating; stop the camera if restoration fails |
| Bench controls/cleanup | Held controls could replay, and one cleanup exception could prevent other stops | Observe edges during execution, consume each attempted trigger hold, and nest cleanup in `finally` |

The independent pinhole oracle crosses three pitches, five horizontal offsets, three vertical offsets and four robot headings. It derives the optical ray `[tan(tx), tan(ty), 1]`, rotates it by pitch, intersects the floor, then rotates into the field; it does not reuse `LimelightCalibration.project`.

## Input and state traces

Camera:

- Fresh matching detector frames publish once. A matching timestamp repeated in a new SDK object does not create another frame.
- Missing, stale, wrong-pipeline, invalid-localization, invalid-mounting and corrupt-latency frames supply no new map-clearing evidence. Fresh analyzed detector frames with no detections may clear only their capture-time visible region.
- Raw confidence 0 and 1 are valid fractions; negative, NaN, infinity and values above 1 are rejected. Multiplying verified percentage input 83.984375 by an explicitly selected 0.01 scale produces 0.83984375.
- Frame age 250 ms and combined age/latency 500 ms are boundary cases; larger total latency is rejected. Cached getters expire even without another update.
- Stop clears camera-derived health readings and usable results. Failed initialization can be retried. Failed snapshots and failed pipeline switches remain reported.

Map:

- Null frame, null/nonfinite capture pose, invalid configuration and nonpositive sequence preserve tracks.
- A sequence 2 or repeated 3 after sequence 3 is inert; fresh empty sequence 4 clears the visible wedge.
- Default safe radial boundaries are 11 and 57 inches after the 3-inch margin; values just outside are invisible. Angular safety margins are checked independently.
- A level pinhole camera at height 10 inches does not see a floor point 15 inches ahead within its vertical field of view; it does see a point 30 inches ahead. Pitching down 30 degrees brings the nearer point into view.
- Track replacement preserves matching IDs; out-of-view tracks survive. Capacity is clamped to 1–64; raw map scanning is capped at 32 entries, including rejects. The camera scans at most 128 detector entries. These bounds intentionally trade dense-frame coverage for execution time.

Planner:

- Empty/expired input produces no fitting run. Nonpositive capacity means one unbounded tour; positive capacity and horizon are bounded.
- Null/nonfinite poses, malformed run arrays and invalid numeric settings are rejected or filtered at their documented entry point. Duplicate candidate IDs cannot be planned twice.
- First run starts at live odometry; later runs start at the scoring depot. Pickup dwell and final heading settle enter predicted duration; caller-controlled scoring contributes overhead.
- Fitting runs form a prefix; committed time never exceeds remaining time in the checked cases. Output coordinates and diagnostic times are finite.
- The independent exhaustive oracle inspected **34,444 assignment states over 100 fields**. It enumerates picked subsets, orderings and run boundaries using its own motion-cost calculation. Fourteen cases had a smaller heuristic haul than the feasible optimum; these are documented approximation gaps, not constraint violations. The user requested fast execution rather than perfect path finding.
- Candidate, iteration, local-search and improvement-time limits are checked, including zero optional budget and oversized input maps. The final main-checkout run observed a maximum solve of 17.3601 ms across its budget cases; loaded-host runs can be much slower. The default 15 ms limit is an improvement budget, not a guaranteed whole-call latency.

Collection runner:

- `IDLE -> DRIVING` occurs only after a fitting plan; already-busy and no-fit requests return false. An empty map away from the depot stays IDLE.
- Each pickup has its own path. Dispatch alone does not claim collection. The follower must arm or reach the target during the arming window.
- Successful arrival optionally dwells, removes only the reached/matching target and advances to the next leg. Home completion also requires the scoring heading.
- Never-busy, missed and timed-out pickups remain uncollected. At most one replan occurs; failed positions are excluded even when redetected under new IDs. Recovery returns home, or aborts on home failure/deadline.
- Leaving during dwell, invalid odometry, cancellation and runtime drive failure cannot claim a pickup. Total remaining time bounds the whole run.
- `COMPLETE` describes the tested return tolerance only. It neither proves intake physically succeeded nor triggers a shooter. Caller still owns both mechanisms.

Relocalization and training:

- Busy drive, disconnected camera, invalid origin and invalid limits reject a correction attempt. Concurrent attempts cannot replace an active one.
- `IDLE -> LOOKING -> SETTLING -> IDLE` is nonblocking. Fresh tag solutions require tag evidence and correct pipeline, then pass motion, field-bound and jump gates.
- Motion anywhere during the look window remains a rejection even if the robot returns to its original pose. A solution arriving after the deadline, including a zero-duration look window, is rejected.
- Every completed/rejected look restores the detector. Pose-setting exceptions restore before propagation; failed restoration disconnects/stops the camera rather than hiding the failure.
- Training uses a unique session namespace plus an incrementing attempt counter. Failed captures consume names. Automatic capture waits two seconds, makes one attempt per elapsed interval and remains idle when disabled.

## Hardware and build limits

The inherited range curve, camera height/pitch/offsets and motion constants require measurement on F.R.O.G. The pinhole model remains disabled by default. Verify detector classes/pipeline configuration, angular signs, localization frame and pickup/return tolerances on the robot before enabling the bench OpModes. Position-based pickup cannot prove the intake obtained a pollen.

The full offline Gradle compile and a no-daemon retry previously failed before Java compilation with `java.io.IOException: Unable to establish loopback connection`. Standalone SDK compilation and the above harnesses passed; this does not establish a successful Android APK build.

Primary API checks: [Limelight FTC Java programming](https://docs.limelightvision.io/docs/docs-limelight/apis/ftc-programming) and [Limelight JSON results specification](https://docs.limelightvision.io/docs/docs-limelight/apis/json-results-specification). The JSON example uses `conf: 0.83984375`; installed FTC SDK 12.0.0 `DetectorResult` passes the JSON `conf` value through unchanged. This explains the fractional-confidence correction despite the SDK getter's percentage wording. Camera angular sign conventions still need a physical check; the port follows the Java angle interface and source convention.
